# Android

The native Kotlin/Compose app: manual-entry-first, with an optional paid Claude-vision Scan (see Scan Proxy's `CONTEXT.md`; what the user is told for each way a Scan can end, and when a retry keeps the request id or offers Try again, is its "Scan outcomes" entry, which `ScanOutcomesFixtureTest.kt` checks this app against through `test-vectors/scan_outcomes.json`) for any of the three documents.

Android's `Rig`/`Breakdown`/`Item`/`Tone`/`Verdict` model mirrors Core/Web's shape exactly (`RecentRig.kt`, `BreakdownItem.kt`, `Tone.kt`, `VerdictInfo.kt`) but is its own independent implementation, not a shared library — see `CONTEXT-MAP.md`'s Relationships and ADR-0001. Definitions for those terms live in `src/hdttools/CONTEXT.md`; this file only covers what's genuinely Android-specific.

## Language

**Disclaimer**:
A blocking, once-per-app-session acknowledgment ("Experimental Tool — Not for Safety Decisions") shown before the first Results screen. Session/process-scoped only — never persisted, so it re-appears every app launch. Android's wording is deliberately its own, not shared with Web/Streamlit (see `CONTEXT-MAP.md`'s Relationships — each platform independently implements this gate), because the original text assumed OCR'd photos and Android defaults to manual entry.

**Entry Module**:
Which of the three documents (Truck Tag, Trailer Tag, or Scale Ticket) a given screen is currently collecting data for — the app's own routing/UI concept, not a Core concept.

**Check**:
One run through the three Entry Modules for one rig, from picking or starting the rig to Results. A Scan belongs to the Check and the screen it was started on: when the user picks or starts another rig, or leaves that screen (backs out or moves on), that Check is over for the Scan, and a result that arrives later is not used. Turning the device is not leaving.

**Account**:
The shared RigCheck sign-in (Supabase Auth; email + password and Google; Apple is deferred to the iOS port, #77) that Android shares with Web — the same account on every device. Its id is also the RevenueCat app user id, so purchases and the Scan Credit balance follow the account (ADR-0003, ADR-0004). Asked for only when something needs it — buying or scanning; the free manual-entry flow never requires one. Signing out affects this device only. Anonymous-id beta users are not migrated.

**Plan** (Free or Pro):
Whether the signed-in Account has the RevenueCat `pro` entitlement, however and wherever Pro was bought — a Pro bought on Web shows as Pro here, and the other way round (#27, ADR-0003, ADR-0006). Shown on the Paywall; read again when the Paywall opens and after a purchase or restore, since it can change on another device. Not known (signed out, RevenueCat not yet linked to the Account, or the read failed) is shown as nothing, never as Free. The Scan Credit balance follows the Account the same way and is read from the same place.

**Paywall** ("Get More Scans"; titled "Unlock Pro" while the Account is Free):
What the Plan decides the Account may buy (#101, ADR-0006's 2026-10-12 amendment): a Free Account is offered Pro (the Offering's lifetime package) and no scan packs; a Pro Account is offered the scan packs and not Pro; while the Plan is not known nothing is offered, with Try again. Buying Pro keeps the Paywall open: the Plan and Scan Credit balance are read again and the packs replace the Pro offer. Buying a pack closes it. Pro is told from a pack by what RevenueCat reports about the package (lifetime package type; any other one-time package is a pack, a subscription is neither), never by product id; prices come from the store. The Android SDK does not report consumable versus non-consumable, which is why the lifetime package type is the marker. The scan service still checks only the balance, so this is enforced here, not there. It scrolls when taller than the screen, and a Back control above the scrolling part leaves it from every state (#186); like every screen, it sits inside the system bars (`RigCheckApp`'s one padding rule). The re-skin (#196) keeps all of that: see **Paywall, Account and the two Scan dialogs (#196)** below.

**Design tokens** (#191):
The designer's `docs/android-redesign/design-return/tokens.json` (colours, 17 named text styles, radii, elevations, sizes, spacing, opacities, the Material 3 roles) written as code in `ui/theme/`. The JSON is the design's record and the code must equal it: `DesignTokensTest` compares both ways and fails on any difference. Light theme only, no dynamic colour. The fonts, Outfit (display) and DM Sans (body), are bundled in `res/font/` (variable files, SIL Open Font License; the texts are in `android/font-licenses/`), so the first launch offline looks the same; `RigCheckFonts.Fallback` is the design's own fallback ("system sans-serif"), and every Material 3 text slot is set to one of the named styles, never left on the platform default.

**Shared components** (#191):
The reusable pieces of the design's `components.md`, named `RigCheck*` in `ui/components/` (top bar, icon button, button in four kinds, text field, option card, rig card, step indicator, verdict band, breakdown row, notice card, badge, progress bar, empty state) plus the scan balance chip. Each exposes the colours it draws with as a plain function (`rigCheckButtonColors(kind, state)` and so on), so its Compose test can hold the text colour to WCAG AA against the fill it sits on. Every tappable one has a touch area of at least 48 x 48 dp. They replace the ad-hoc copies in the screens only as the re-skin tickets (#192 to #196) adopt them, and `implementation-status.json` records which elements are built.

**Entry screens (#193)**:
The Truck Tag, Trailer Tag and Scale Ticket screens share one skeleton, `EntryScreenFrame`: the top bar (Back, title, step indicator, and on the Truck screen the balance chip) and the reference card are pinned, the form is one scrolling column, and the primary action is pinned in `RigCheckFooter`. With the keyboard open the bar is compact and drops the step indicator; the card scrolls with the form instead of staying pinned when the screen has less than 420 dp left for everything (a short phone with the keyboard up), and takes its compact size (a 44 dp strip of the photo) on a screen under 700 dp high or at a font scale of 1.6 or more. Back is off while the Truck screen's stand-alone Scan is out. The reference card (`PinnedReferenceCard`) follows the focused field (#199): `ReferenceSpots` (`ui/ReferenceSpots.kt`) stores, for each Truck and Trailer field that has a printed line on the label (Truck: GVWR, Front GAWR, Rear GAWR; Trailer: GVWR, GAWR per axle, UVW), a crop rectangle (three lines of the label) and the printed line, as fractions of the photo, with the badge's name; the card shows that crop with the line outlined in orange and the badge beside the hint "Tap a field to see its spot on the tag". With no field focused, or a field with no line on the label (a description, a name, the GCWR, the stand-alone weight, the axle count), it shows the label's first lines with no badge. `spotWindow` turns a rectangle into the part of the photo drawn (the smallest window of the card's shape that holds it, centred on it); the compact strip shows the focused line only. A screen reader hears the field in the photo's description and the badge is a polite live region. There is no gesture on the card: the press-and-hold zoom is gone. The stand-alone weight label, field, pin-weight slider (`RigCheckSlider`) and Scan button sit inside the orange panel, below the Scan button, as drawn. The Scale photo shows the part of the ticket that holds the scale location and the four weights, with numbered badges 1 to 5 on those lines; the same numbers are in the legend and in front of the field labels (`RigCheckNumberBadge`).

**Disclaimer and Results screens (#194)**:
The Disclaimer is one page that scrolls (the icon tile, the title, both paragraphs; the wording is untouched and locked byte for byte by `tests/test_android_copy_lock.py`) with "I Understand, Continue" pinned in `RigCheckFooter`, so a large font or a small phone no longer pushes it off the screen; it has no top bar. The Results screen has the top bar pinned (Back, which does what the system Back button does, then the Rig's name over the date) and "Start another check" pinned in the footer; between them the verdict band, the notices, the breakdown card and the footer note scroll as one page, with no list inside the card. The notices come in the frames' order: the estimate (`EstimatedFiguresNotice`, the warn notice without an icon of its own, its title keeping its emoji), the Garage notice with "Get Pro for a bigger Garage" under it as a ghost button, then the History notice. A breakdown row (`RigCheckBreakdownRow`) is flat in the card: the status icon, the label, a status badge that says "Within limit", "Over limit" or "Not checked" in words (a failing row and the failing verdict never rest on colour alone: each has its own icon and its own words), a 10 dp bar, and "A lb of B lb" with the percentage; a row with a note also has a chevron, a 48 dp target laid over the row's padding so the row is as tall as one without (about 104 dp), and a tap on the row itself opens the note too. A 1 dp rule sets a row off from the one above it when either of the two has a note, as the frames draw it. From font scale 1.6 the badge goes under the label, and under 380 dp of width the verdict band puts its icon above its words.

**History screen (#195)**:
A top bar (Back, which does what the system Back button does, and "Check History") is pinned; under it the subtitle, the limit notice and the entries scroll as one list. The limit notice is the info notice with "Upgrade to Pro" under it as a full-width ghost button. An entry is a white card with the Rig's name over its day and the verdict as a pill badge (`RigCheckBadge`: green "Safe to Tow", red "Over Limit", purple "Partially Checked", outlined "Not Enough Info", each with the icon the verdict band uses, so a verdict is never told by colour alone); from font scale 1.6 the pill goes under the name and the day. With no checks the screen draws the empty state, a dashed panel with the logo (`RigCheckLogo`, shared with the Rig picker) and the one line of words. Nothing is pinned at the bottom: the screen has no action of its own besides Upgrade to Pro.

**Paywall, Account and the two Scan dialogs (#196)**:
Both screens have the pinned top bar (Back and the title; the Account's Back goes where Not now goes) and a pinned footer (`RigCheckFooter`): Restore purchase on the Paywall, Not now on the Account screen, so the 3-button navigation bar can no longer cover them and a large font cannot scroll them away. Between them the body scrolls. The Paywall's body is the beta notice (the info notice in the scan tone, bold; beta builds only: a production build leaves it out and everything below moves up 80 dp), the "Buying for" line with a ghost Sign out, the plan as a pill, the explainer and the offers. A Free account's one offer is a large tint-purple Pro card with the price button inside; a Pro account gets a white row per pack with a compact price button, which grows to the store's own text ("CA$12.99 one time") and never wraps it. A purchase or a restore is answered in a Snackbar (`RigCheckSnackbarHost`: ink fill, white text, 14 dp radius, 16 dp margins, 4 s, no action) above the footer, one at a time, the same words the Toast had. A bought pack is the exception: the screen closes at once, and a Snackbar would close with it, so that one confirmation stays a system Toast (owner, #196). The Account form uses the shared `RigCheckTextField` (the same field as every other screen, with `keyboardType` and `visualTransformation` added to it for the email and the password), the reason in muted body text, the sign-in answer as a line of words in `danger-text` (an error) or a notice (info), the toggle and Forgot password one under the other as ghost buttons, a divider, Continue with Google as a secondary button, Send feedback and Not now. `ScanErrorDialog` and `LateScanDialog` use `RigCheckDialog`: the title, the message, then the buttons stacked at 52 dp (the first next step primary, any other secondary, OK a ghost button last). The Google glyph and the Apple one are not drawn: the design leaves the Google mark to its official asset, which is not in the repository yet.

**Rig picker header and Chooser (#192)**: the Rig picker's teal bar carries the logo, name, tagline and balance chip, and an account row (`RigCheckAccount` in `ui/components/RigCheckAccountStatus.kt`): "Signed in as <email>" opens a bottom sheet whose Sign out is the second tap; "Not signed in" with Sign in goes to the Paywall route (which shows the sign-in screen), as the chip does. Signing in there returns to the screen the sign-in was started from (#206): the front page from the picker, the check's own screen from inside a check; `RigCheckNavHost` pops the Paywall route on the change from signed out to signed in, and never on opening the app signed in or opening the account page later. An account still being looked up has no row. The row only exists on the picker; a Scan belongs to its Chooser, whose top-bar Back is disabled and whose overlay covers the whole screen while a Scan is out. At a font scale of 1.6 or more the chip moves under the title (`chipBelowTitle()`), and on the picker with the keyboard open the tagline and account row are dropped. The photo-source dialog and later dialogs use `RigCheckDialog`. The picker's header divider no longer exists; `picker.header_divider` is `removed` in the design.

**Scan balance chip**:
The pill that shows the Scan Credit balance and opens the Paywall (a white pill, 48 dp high). Signed out the balance is not known and the chip says "0 scans" (nothing can be scanned); an account whose balance is still loading shows "…". `creditChipLabel` is the one place that decides it.

**Beta kit** (#182):
What a beta tester sees that production does not, on top of the beta build (#174). "Send feedback" (on the Rig picker and the sign-in screen) opens an email to the one feedback address, `FEEDBACK_EMAIL` in `ui/util/Feedback.kt`; a phone with no mail app is told so and given the address. The Paywall shows "Beta: test payments" only when `BuildConfig.IS_BETA` is true. The address is the same on Web and in `docs/BETA_TESTER_GUIDE.md` (`tests/test_beta_feedback_address.py`).

**Crash report** (#184):
A crash is saved on the phone, and the next launch asks "RigCheck closed unexpectedly last time. Send details?". No third-party service: nothing leaves the phone unless the tester taps **Send**, which opens an email to `FEEDBACK_EMAIL` with the report as the body; **Not now** deletes it. The report is one small file in app-private storage (a newer crash replaces an unanswered one) holding the exception class names, the stack frames, the app version, the Android version, the device model and the time. **Exception messages are never recorded**, because that is where an email, a token or a typed Rig value would leak. The app still crashes as before: the handler that was installed first runs after the report is written, and a failed write does not stop it. `installCrashCapture` runs first in `RigCheckApplication.onCreate`; the question is `CrashReportPrompt`, mounted in `MainActivity`.

**Garage** (#31):
The set of a user's saved Rigs (a **Rig** is one member). Signed in, it lives in the **Account** (Supabase `garage_rigs`, ADR-0005), the same on every device, so a Rig added on Web is in the Rig picker here and the other way round; the picker reads it again whenever it is on show. Signed out, it is the Rigs kept on this phone (the free flow is never gated), hidden while signed in and back after sign-out; they are not carried into the Account (Web offers that import, Android does not yet). The Plan's cap is enforced by the database, not the app: a finished check saves its Rig (updating the Rig of that nickname if there is one, which uses no room, else adding it), and one request is retried once with the same idempotency key, so a lost reply never saves a Rig twice. A full Garage refuses the new Rig; the check and its Results are unaffected and the Results screen says the Rig wasn't saved (a Free Account is offered Pro there, as on Web). The app tells the database the Plan (`p_pro`, from the same read as the **Plan**) and the database picks the cap; a Plan not known is sent as unknown and gets the Free cap. Nicknames match ignoring case and surrounding spaces, as on Web. A Rig's truck and trailer are stored in Web's field names (`GarageWire.kt`: `description` is the tag's `manufacturer`, `name` is `vehicle_name`, `gvwrLb` is `gvwr_lb`); fields only Web keeps (a VIN, tire sizes) are carried through untouched when a Rig is saved here. A signed-in user deletes a Rig from the Rig picker (#169, as on Web's `RigDelete.tsx`): the bin on a Rig's card asks "Delete …? This frees its spot in your Garage and can't be undone." first, and on "Yes, delete" the Rig leaves the account and the picker at once, so a full Garage has room again without waiting for the list to be read. A delete that fails says so, keeps the Rig and offers another try; a Rig another device already deleted counts as deleted, not an error. Signed out there is no delete control: the Rigs kept on this phone cannot be deleted (as on Web).

**History** (#32):
The list of a user's past, completed checks (one **Check** is one entry: date, rig nickname, Verdict), opened from the Rig picker's "History" button. A record of results, not of Rigs. Signed in, it lives in the **Account** (Supabase `history_entries`, ADR-0005), the same on every device, so a check done on Web is listed here and the other way round; it is read again whenever the History screen is on show. Signed out, a check is kept only for the app session and is never saved; the Account's own list replaces it on screen at sign-in and it comes back at sign-out, and it is not carried into the Account. The newest checks are kept and the oldest dropped by the database function `add_history_entry`, a count taken from `plan_caps` by Plan (the same cap and pruning as Web, which is why Android sends the Plan as `p_pro`: true Pro, false Free, and not known sent as unknown, which gets the Pro count because pruning a Pro Account's History cannot be undone). The History screen tells a Free Account whose History is full what Free keeps and what Pro keeps, with "Upgrade to Pro". A finished check is recorded once when its Results screen first appears (turning the device does not record it again), with one request retried once under the same idempotency key so a lost reply never records it twice; a check the Account could not save is still shown as a result, with a notice on Results. An entry is read and never edited or deleted by the user. A verdict stored as a word this app does not know is left out, not shown as another verdict. Android has no History filters yet (Web's All rigs, per-rig, Within limits, Over limit pills).

**Scan notice**:
The note above the fields of the entry screen reached after a delivered Scan (Truck Tag, Trailer Tag, Scale Ticket) that did not read every field: "A Scan was used and nothing could be read…" when it read none, or the unread fields named when it read some (#120). The Scan was charged whatever it read, so this tells the user one was used. A notice, not a failure: no Try again. Manual entry never shows it; it goes away when the user leaves the screen or types in the missing fields.

## Open question, not yet a term

`ANDROID_DESIGN_BRIEF.md` describes a two-tier purchase model (a "lifetime unlock" with preset credits, plus separate consumable "credit packs"). The Paywall now makes that distinction (see **Paywall** above: Pro and scan packs), but don't treat "lifetime unlock"/"credit pack" as established vocabulary — the terms are Pro and scan pack, and pricing and pack sizes are still undecided (#33).
