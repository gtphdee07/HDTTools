# Web

The React + Vite + TS frontend: the paid-product-in-progress surface that wraps Core's OCR/breakdown math in a guided, multi-step flow. Hosted as a static site on Cloudflare Pages (push-to-deploy).

## Language

**Rig**:
A user-named, reusable pairing of a Truck Tag and Trailer Tag (a `RecentRig`: nickname + truck + trailer + last-used timestamp), saved so a returning user can start a new check without re-entering or re-scanning both tags. Not a Core concept — Core's `compute_breakdown` takes bare truck/trailer/scale data with no notion of a saved, named pairing. This is the product's central noun (the app is "RigCheck"); Android maintains its own equivalent concept independently — see `android/CONTEXT.md` once written.
_Avoid_: vehicle combination, setup.

**Garage**:
The collection of a user's saved Rigs (not a single Rig). Capped per account — a count, not unbounded storage — with the cap itself a pricing-tier detail, not a Garage-concept detail. Account-synced per ADR-0005, superseding the device-local-only scoping in ADR-0004: for a signed-in user the Garage lives in Supabase (`garage_rigs`; the cap is enforced by the database function `add_rig`, which takes it from the `plan_caps` table by plan: a larger cap on Pro than on Free), identical on every device; a signed-out visitor keeps a browser-local Garage (`recentRigs.ts`), which is not carried into the account on its own: it is hidden while signed in and comes back on sign-out. On the first sign-in to an account on a browser that holds such Rigs, the app offers to import them (`garageImport.ts`). Accepting adds them through the same capped, idempotent add path as any save, one idempotency key per Rig that is kept across a retry of an interrupted import; a Rig the account already holds under that nickname is left as it is, and Rigs the cap leaves out are named to the user. Declining, or finishing, ends the offer for that account on this browser; the browser's own Rigs are never changed either way. One Rig per nickname, in the browser list and the account alike: nicknames are compared ignoring case and surrounding spaces ("Truck A" and " truck a " are the same Rig; `nickname.ts` is the one rule, matching the account's `lower(btrim(nickname))` index), saving under a matching nickname refreshes that Rig instead of adding one, a refreshed Rig keeps the spelling it was first saved under, and a nickname is stored without its surrounding spaces. A full Garage refuses a new Rig with a message; it never silently drops the oldest. On the Free plan that message offers "Upgrade to Pro" (to the Account screen, and back to the check afterwards), and so does an import that did not fit; a full Pro Garage names Pro's cap and offers nothing. The way out of a full Garage is deleting a Rig: the user picks the bin on a Rig, in the check's Rig list or on its "Your Rigs" card on the Dashboard (one shared control, `RigDelete.tsx`), confirms, and the slot is free at once (a failed delete says so and keeps the Rig); a signed-out visitor's browser-local Garage has no delete control.
_Avoid_: using "Garage" and "Rig" interchangeably — Garage is the set, Rig is one member of it.

**Wizard**:
The guided, five-step flow that produces one Breakdown: select a Rig (step 0), enter/scan the Truck Tag (1), Trailer Tag (2), Scale Ticket (3), then view Results (4). Each step has its own sub-state (`upload` / `processing` / `review` / `error` / `finalizing`) tracking where the user is within that step's own data-entry flow.

**History**:
The list of a user's **past, completed** checks (`HistoryEntry`: id, date, rig nickname, Verdict) — a record of *results*, not to be confused with a Rig, which is a *reusable input* (a saved truck+trailer pairing) rather than a past outcome. Account-synced per ADR-0005, like the Garage: for a signed-in user History lives in Supabase (`history_entries`), identical on every device, and the database function `add_history_entry` keeps only the newest checks, dropping the oldest as a new one arrives (a fixed count taken from `plan_caps` by plan, larger on Pro). The History screen tells a Free account whose History is full what Free keeps and what Pro keeps, with "Upgrade to Pro". A retried save counts once (the client reuses one idempotency key across its retry). An entry is a record of a past result: it is read and never edited or deleted by the user. A signed-out visitor's checks last only for the visit and are never saved; they are not carried into the account on sign-in (the account's own History replaces them on screen, and signing out brings them back). A check the account could not save says so and is still shown as a result.

**Dashboard**:
The app's home screen, showing recent activity and entry points into the Wizard and History.

**Pro**:
The one-time, lifetime paid plan, as opposed to Free. It is shared across platforms through the account (ADR-0003/0006) and is backed by the `pro` entitlement *object* in RevenueCat; that is RevenueCat's own record, not the reserved glossary term **Entitlement** (the question of which system is the source of truth for paid status — see `workers/scan-proxy/CONTEXT.md`). A signed-in Free user buys it from the paywall on the Account screen, in RevenueCat's modal checkout; the Web app only reads the Pro status and the **Scan Credit** balance (the `SCAN` virtual currency) back from RevenueCat, it never grants either. Pro also raises the **Garage** and History caps. The database has no record of who is Pro, so each Rig or History save carries the plan the app reads from RevenueCat (`plan.ts`), and the larger cap applies as soon as Pro shows on the device, on another device once its tab is shown again. A plan the app could not read is sent as unknown, which the database treats as Pro so a Pro account is not refused a Rig or pruned over a failed read (the Pro cap still bounds storage). The app's word is trusted, by the owner's decision on #30: a hand-edited request could claim Pro for storage, not for scans, which the Worker still charges. The cap numbers are placeholders in the `plan_caps` table, edited there, pending launch pricing (#33). RevenueCat grants the starter scan bundle server-side, so after a purchase the Account screen rechecks the balance over a short, bounded window ("Updating your scans...") and, if it never changes, says scans may take a minute; the user stays on Pro throughout. The paywall states that results are not certified DOT weights; that is separate from the **Disclaimer** gate.
_Avoid_: Entitlement, Premium, subscription (it is a one-time purchase), "Scan credits" in lower case (the term is **Scan Credit**; the Account screen says "Scan Credit balance").

**Scan pack**:
A consumable top-up of the **Scan Credit** balance (ADR-0006), bought from the "Buy more scans" card on the Account screen by a **Pro** user (a Free user is offered Pro, not packs, so scans are not sold without Pro), in the same RevenueCat modal checkout as Pro. A pack adds scans only: it never changes the plan, so the Garage and History caps are untouched. Which packs are on sale, their titles and prices, and how many scans each grants are RevenueCat's configuration; the Web app lists the offering's web-purchasable consumable packages other than Pro (or just those named in `VITE_REVENUECAT_SCAN_PACK_PACKAGE_IDS`) and only ever reads the new balance back, using the same bounded "Updating your scans..." recheck as the Pro starter bundle. No packs configured means no card.
_Avoid_: credit pack, top-up, bundle (the **Pro** "starter bundle" is a different thing, granted with Pro).

**Scan**:
Defined in `workers/scan-proxy/CONTEXT.md` (the Scan Proxy Worker is the shared "scan service": it spends one **Scan Credit** before reading and refunds it if nothing is read). On Web, a Scan reads a photographed Truck Tag, Trailer Tag or Scale Ticket, including the tow-vehicle-only ticket on the Truck review step. Who may scan: a signed-in **Pro** user with at least one Scan Credit. Anyone else is shown the one thing in their way instead of "Extract Data": sign in (signed out), upgrade to Pro (a Free user, since scans are not sold without Pro), or buy a **Scan pack** (a Pro user with none left); each leads to the Account screen and back to the same check. Typing the numbers in is always open. The Web app sends the account token and a `client_request_id`; charging, refunding and deduplication are the service's. The id stays the same across retries of a photo whose answer never arrived (so a retry is charged once) and is new once the service has answered. A Scan on a Truck Tag, Trailer Tag or Scale Ticket that is delivered but leaves fields blank still goes to the review step, which says so in a notice above the fields rather than as a failure (no Try again, `scanNotice.ts`): nothing read says a Scan was used and offers "Choose a different photo" (back to the photo step; nothing is sent until Extract Data), some read names the fields not read, all read shows no notice; fields marked optional (stand-alone weight, truck GCWR, axle count) are not counted, and skipping the photo used no Scan so it shows none. An answer that is delivered but has no weight in it on the tow-vehicle-only ticket is still a charged Scan (the service does not read document contents, so it does not refund): the message says the Scan was used and that trying again uses another, and offers "Choose a different photo" and "Type it in", not "Try again" (the same photo through the same model will probably read the same, and sending it again is another paid Scan). The stand-alone ticket's "Try again" is offered only where sending the same photo again can help (`ScanError.canTryAgain`): the service could not verify the account, could not read the photo (refunded or not), could not confirm the balance, or gave no usable answer (no connection, an unreadable reply, a timeout). After a refused account token, a rejected request or a photo that cannot be sent, the next step is signing in again or a different photo instead. When the service refuses the account token (`unauthorized`), the scan gate stops showing the scan count and offers "Sign in again" for as long as that token is the one in use: it ends the refused session, so the Account screen shows the sign-in form, and leads back to the same check with the photo still chosen. A photo the service cannot take (a format it does not read, or over about 3.5 MB) is converted or shrunk in the browser when possible, else refused before anything is sent; that message, and the one for a request the service rejects, say nothing was used and never repeat the service's own wording. A Scan always lands in the check that started it: while one is in flight (a photo being read, or the tow-vehicle-only ticket) the check cannot be left or restarted, with a short "Reading your photo..." note saying why; and an answer that still arrives for a check that is no longer the current one is dropped without touching the new check, though the Scan Credit balance on screen is read again. So that a service that never answers cannot hold the user in the check, a Scan is given up on after 60 seconds for the whole exchange (sending, waiting, reading the reply; longer than the Worker's own worst case of 45 seconds, since the Worker makes one Claude attempt and does not retry it; see "Time limits" in the Scan Proxy's `CONTEXT.md`): the message says it took too long, and it counts as a lost answer like a dropped connection, so the retry keeps the request id and is charged once. What the user is told for each way a Scan can end, and when a retry keeps the request id or offers Try again, is the "Scan outcomes" entry in `workers/scan-proxy/CONTEXT.md`; `src/scanOutcomes.test.ts` checks this app against its fixture, `test-vectors/scan_outcomes.json`.
_Avoid_: OCR, extract (the button says "Extract Data" for history's sake; the product noun is **Scan**), "scan credits" in lower case.

**Disclaimer**:
A session-scoped acknowledgment gate shown before results, independently implemented per platform with its own wording — see `android/CONTEXT.md` for the fuller definition and `CONTEXT-MAP.md`'s Relationships.
