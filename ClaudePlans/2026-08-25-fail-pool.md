# Fail-pool: known-illegible images testing the failure path itself

## Context

Item #13's design (`FUTURE_CONSTRAINED_RANDOM_OCR_TESTING.md`) names the
fail-pool as the next piece after the pass-pool (schema, resolver, and a
real regression test all done 2026-08-25): a pool of known-illegible
images, each carrying an expected *failure signature*, proving a real
OCR failure funnels into the app's graceful "Not Enough Information"
path rather than silently accepting garbage as data.

Investigated this session (read-only, no files changed yet): item #11's
10 F-150 photos are still on disk at `ExampleDocs/scans/truck/f150/`
(never deleted — only reverted out of `golden_fields.json`'s `"photos"`
section, per that item's "document, don't build" decision) and are
exactly the fail-pool's ideal first fixture set — zero new photos
needed, same precedent the pass-pool set with `AddieTag.jpg`/
`GooseTag.jpg`. Ran the real pipeline against all 10 just now to confirm
the exact failure signature, not assume it:

```
20260824_141527.jpg -> manufacturer=None, gvwr_lb=None, front_gawr_lb=None, rear_gawr_lb=None
... (all 10 photos, same result on all four fields)
```

All 10 photos return `None` for the same four fields — `manufacturer`,
`gvwr_lb`, `front_gawr_lb`, `rear_gawr_lb` — every time, matching
`golden_fields.json`'s own `truck_tag` field set exactly (`AddieTag.jpg`
tracks the same four). Some *other*, untracked fields (`vehicle_type`,
`vin`, tire specs) occasionally pick up unrelated OCR noise, but those
never feed `compute_breakdown` and aren't part of this signature.

Confirmed the field names line up with `compute_breakdown`'s truck dict
directly (`tests/test_breakdown.py`'s `_TRUCK` fixture uses the same
keys), so `compute_breakdown(extracted, {}, {})` on this real
Tesseract-vs-garbage-photo output should reach the same `"insufficient"`
verdict `test_blank_rig_reports_not_enough_information_not_a_false_pass`
already proves for a hand-written `{}` — this test proves it for a real
photo's real garbled OCR output instead.

## Goal

A real, TDD'd fail-pool regression test proving that a randomly-picked
known-illegible photo (a) produces the exact documented `None` failure
signature under real Tesseract, and (b) that signature funnels into the
app's real "Not Enough Information" degradation path — not a silent
false pass.

## Steps

1. **New `fail_pool` section in `ExampleDocs/golden_fields.json`**, a
   self-contained schema (unlike `pass_pool`, no reference into
   `"photos"` needed — these images were deliberately never added
   there, and the "golden truth" here *is* the failure signature
   itself, not a value to protect from duplication):
   ```json
   "fail_pool": {
     "_readme": "...",
     "truck_tag": [
       {
         "vehicent": "f150_blue_goose_uncropped",
         "images": ["scans/truck/f150/20260824_141527.jpg", ... all 10],
         "expected_none_fields": ["manufacturer", "gvwr_lb", "front_gawr_lb", "rear_gawr_lb"]
       }
     ]
   }
   ```
   (typo above is illustrative only — will write `"vehicle"` correctly).
   `_readme` documents: why these are self-contained instead of
   referencing `"photos"`, why the signature is `None`-per-field rather
   than a golden value, and that this reuses item #11's own investigated
   finding rather than a fresh guess.

2. **New `scripts/fail_pool.py`**, mirroring `scripts/pass_pool.py`'s
   shape exactly: `resolve_fail_pool_image(doc_type, rng=None) ->
   tuple[str, dict]`, picking one registered vehicle then one of its
   images at random, returning `(filename, fail_pool_entry)`.

3. **TDD**: write `tests/test_fail_pool_regression.py` first, watch it
   fail for real (`ModuleNotFoundError` before step 2 exists), then
   implement step 2 to make it pass — same red/green sequence
   `tests/test_pass_pool.py` and `test_pass_pool_regression.py` already
   followed. The test, parametrized over `doc_type` read dynamically
   from `golden_fields.json`'s `fail_pool` keys (today: just
   `truck_tag`):
   - Resolves one image with an **unseeded** `random.Random()`.
   - Runs the real pipeline (`ensure_tesseract_configured` →
     `open_image`/`preprocess_image`/`ocr_text` → `_parse_truck_tag`).
   - Asserts every field in `expected_none_fields` really is `None` in
     the real extraction (the OCR-level signature check).
   - Calls `compute_breakdown(extracted, {}, {})` and
     `verdict_for(items)`, asserting every row's `tone == "insufficient"`
     and `verdict["headline"] == "Not Enough Information"` — the
     app-level degradation check, generalizing item #11's originally
     deferred failure-path test idea into the repeatable fail-pool
     category instead of a one-off.

4. **Update `NEXT_STEPS.md` item #13** and
   `FUTURE_CONSTRAINED_RANDOM_OCR_TESTING.md`'s step-4 list to mark the
   fail-pool done, and mark the outstanding "Tesseract's no-auto-crop
   limitation" test-gap bullet in `NEXT_STEPS.md`'s "Tests still
   outstanding" section as now covered by this fail-pool test (it was
   previously "no test exists for this yet").
